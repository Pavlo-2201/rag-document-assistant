# Оценка ответов на test

Подробности к [README](../README.md) проекта rag-document-assistant.

## Оценка ответов

Выбранный вариант (нарезка 1000/150, `e5-small` + rerank@20, top-5) на 48
test-вопросах, один прогон (`scripts/evaluate_answers.py`, результаты в
`results/evaluation/rerank20__test/`: `report.json`, оценки по каждому вопросу
`per_question.jsonl`, настройки судьи `judge_config.json`, лист для ручной
проверки `manual_review.csv`).

## Как оценивалось

| что | как | чем |
|---|---|---|
| правильность | ключевой термин эталона в ответе | автоматически (`rag/answer_eval.py`) |
| правильность | совпадает ли ответ с эталонным по смыслу: ДА / ЧАСТИЧНО / НЕТ | LLM-судья |
| обоснованность | подтверждается ли ответ процитированными фрагментами: ДА / ЧАСТИЧНО / НЕТ | LLM-судья |
| ссылки | ссылка на фрагмент с цитатой-доказательством; источники вне контекста; несуществующие номера | автоматически |
| поиск отдельно от генерации | был ли абзац с ответом в промпте и среди 20 кандидатов первого этапа | автоматически (`rag/error_analysis.py`) |
| поиск против знаний модели | та же модель отвечает на те же вопросы без документов (closed-book) | автоматически + LLM-судья |
| ручная проверка | не проводилась; `manual_review.csv` подготовлен для неё: ответ, источники, автоматические оценки, вердикты судьи и пустые колонки для человека | — |

LLM-судья — та же Qwen2.5-1.5B-Instruct (q4_k_m, llama.cpp 0.3.16, жадная
генерация, ответ одним словом): другой модели в окружении нет, платные API не
используются. Промпты и критерии — в `src/rag/judge.py` и `judge_config.json`.
Судья оценивает ответы той же модели, а ниже видно, что он почти всегда
говорит «ДА». Его вердикты — шумный сигнал, а не истина, и для выбора
вариантов они не использовались.

Согласие судьи с ключевым термином на 22 ответах — 15 из 22:

| судья: правильность | термин есть | термина нет |
|---|---|---|
| ДА | 12 | 4 |
| НЕТ | 3 | 3 |

- Судья по обоснованности бесполезен на этом наборе: все 18 ответов со
  ссылками он признал подтверждёнными (5 ответов без ссылок получают «НЕТ»
  без вызова модели). В том числе ответ из одних заголовков разделов («[1]
  загрузить файл на сервер [2] загрузка нескольких файлов на сервер») и ответ на
  «чтобы сайт работал без интернета», пересказывающий фрагмент о публикации
  сайта («создать новую страницу без ссылки с другой страницы»). Формально
  такие ответы опираются на фрагменты, но на вопрос не отвечают.
- Судья по правильности снисходителен: ответам без документов он поставил
  «ДА» в 32 из 36 случаев, хотя ключевой термин эталона есть только в 17.
  «ДА» получили, например, `::before` для тени блока (эталон — `box-shadow`),
  `len()` из Python для длины строки, Desmos и GeoGebra для «рисовать графику
  прямо в браузере» (эталон — `<canvas>`).
- Ключевой термин тоже груб. «Изменить адрес страницы без перезагрузки»:
  ответ начинается с неверного утверждения про `Location.replace()`, а
  `pushState()` упомянут только в четвёртом пункте, и термин засчитан. Ответ
  про цикл `for` по массиву верен, но термина (`for...of`, `forEach`) в нём нет.
  Поэтому числа выше — ориентир; окончательную оценку правильности даст
  ручная проверка по `manual_review.csv`.

## Ошибки по этапам

Этап определяется механически по цитатам-доказательствам: есть ли абзац с
ответом среди 20 кандидатов первого этапа, в top-5 после переранжирования, в
ответе модели (`rag/error_analysis.py`). «Верно» — ключевой термин в ответе.

| test | вопросов |
|---|---|
| с ответом: верно | 15 из 36 |
| поиск: абзаца с ответом нет среди 20 кандидатов `e5-small` | 18 |
| переранжирование: абзац был среди кандидатов, но не попал в top-5 | 1 |
| генерация: абзац был в промпте, а ответ без термина или отказ | 2 |
| без ответа: отказ (верно) / ответ (ошибка генерации) | 11 / 1 |

- Главное узкое место на test — поиск: 18 из 21 ошибки. В 14 из них
  страницы с ответом нет даже среди 20 кандидатов, и переранжированию нечего
  поднимать. Вопросы сформулированы бытовыми словами («рисовать графику прямо
  в браузере», «узнать где находится пользователь», «хранить много данных в
  браузере в виде базы»), а ответ лежит на странице, названной по API
  (`<canvas>`, Geolocation, IndexedDB). В остальных четырёх страница найдена,
  но не тот раздел.
- Когда абзаца с ответом нет, модель в основном отказывается (строгое
  правило), но в 7 случаях из 18 отвечает по найденным фрагментам. Один такой
  ответ верен по смыслу (цикл `for` по массиву), остальные мимо: «каким
  методом запрашивают данные с сервера» — «Метод POST» из раздела про
  отправку формы (эталон — GET); «расположить элемент поверх остальных» —
  про позиционирование, но без `z-index`.
- Ошибки генерации при найденном абзаце редки: 2, и обе — отказ, хотя абзац с
  ответом был в промпте. Но у ответов есть постоянные дефекты: модель копирует заголовки разделов вместо ответа и
  ставит `[1]` в начало по привычке. Повтор ловит только ответ из одних
  номеров, а ответ из заголовков со ссылками проходит.
- Единственная ошибка на вопросах без ответа — сочетание клавиш для
  инструментов разработчика в Яндекс Браузере: модель ответила `Ctrl + Shift
  + I` со ссылкой на фрагмент про другие браузеры.
- Парсер. В контексте 6 из 48 вопросов есть следы ошибок разбора (14
  нераскодированных HTML-сущностей вроде `&lt;length&gt;`, один одиночный
  `\`). Четыре из этих вопросов — ошибки, но все отнесены к поиску: абзаца с
  ответом не было среди кандидатов, а следы стоят в посторонних фрагментах.
  Случаев, где ответ испортил именно парсер, на test не видно. Во всём корпусе
  `python -m rag check` находит следы в 190 документах из 2570: 1107
  HTML-сущностей, 40 формул в виде исходника TeX из MathML, 17 одиночных `\`,
  7 пустых инлайн-кодов. Две ошибки парсера, найденные раньше, исправлены (этапы
  «Оценочный набор» (`docs/retrieval.md`) и «Эксперименты» (`docs/experiments.md`)); раскодирование сущностей — в следующих шагах.

## Когда поиск помогает, а когда мешает

Та же модель без документов отвечала на те же 36 вопросов (системный промпт
«Ты — помощник по веб-разработке. Ответь на вопрос по-русски, 1–3
предложения.»). Ключевой термин:

| test, 36 вопросов | с поиском (RAG) | без документов |
|---|---|---|
| термин в ответе | 15 | 17 |
| только у этого варианта | 7 | 9 |
| у обоих / ни у одного | 8 / 12 | |

По одному термину RAG не лучше модели без документов, и это честный
результат для вопросов о популярных основах веба на модели, которая их знает.
Разница — в том, как именно они ошибаются и можно ли ответ проверить:

- Поиск помогает, когда без документов модель уходит в сторону: длина строки —
  `len()` из Python вместо `length`, пробелы по краям — `strip()` из Python
  вместо `trim()`, перетаскивание — общие слова вместо Drag and Drop API. С
  поиском ответ про JavaScript и CSS и со ссылкой на раздел MDN.
- Поиск мешает, когда абзаца с ответом нет в промпте. Тогда строгое правило
  даёт отказ, хотя модель знает ответ сама: `concat()`, `border-radius`,
  `position: fixed`, `gap`, IndexedDB. Это 6 из 9 вопросов, где термин есть
  только без документов: в четырёх абзаца не было среди кандидатов, в одном
  его вытеснило переранжирование, в одном модель отказалась при абзаце в
  промпте. Это цена правила «отвечать только по документам». Ещё хуже
  посторонний фрагмент, который уводит ответ: «Метод POST», «создать новую
  страницу».
- Без документов модель отвечает на всё, в том числе уверенно и неверно (`::before` для тени, `<center>` для выравнивания текста, GPS для
  местоположения пользователя). Ответ RAG либо опирается на конкретный
  фрагмент, который можно открыть, либо честно сообщает, что ответа нет.
